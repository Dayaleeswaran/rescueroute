# Food-rescue coordinator usability session

This is a prepared validation protocol, not a claim that a coordinator pilot has happened. Use fictional records. Obtain permission before recording anyone's feedback, and do not publish their identity or contact details without consent.

## Tasks without coaching

1. Sign in, find Start a rescue, and identify the next task.
2. Turn a donor message into an offer. Explain which missing facts must be confirmed.
3. Find the review queue and explain why pending records are excluded from planning.
4. Preview the absence of the chilled-capable volunteer. Explain the 20-portion difference and whether any real availability changed.
5. Build, inspect, and confirm a plan. Distinguish a draft from a reservation.
6. Follow a volunteer handoff through recipient receipt. Distinguish arrival from delivery.
7. Explain whether the map provides real road directions and whether demo positions represent actual people.

Record task completion, wrong turns, assistance needed, and the participant's own explanation. Measure elapsed time consistently, but report the sample size and do not generalise a small session to all users.

## Before competition submission

- Confirm an eligible food-rescue vertical exists in the actual challenge brief. The urban-air statement shared during development does not establish RescueRoute's eligibility.
- Verify the public URL from a separate device and private browser session.
- Test desktop and mobile layouts, keyboard focus and dialogs, zoom, contrast, and a screen reader.
- Run automated checks and record actual hosted CI results.
- Run `npm run evaluate:live` when the configured provider is available; distinguish live passes from local fallback.
- Verify the public repository contains one branch, stays below 10 MB, and excludes secrets and local data.
- Keep the challenge's two-attempt limit in mind; do not spend a submission attempt on a readiness check.
